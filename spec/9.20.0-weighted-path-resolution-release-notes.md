# Release Notes — 9.20.0 Weighted Path Resolution

`machine:scenario` used to pick among equally long routes arbitrarily, so a scaffold could be routed
through a parallel state when a plain interactive route existed. Routes are now priced and the
cheapest one wins. The price is per state entered — 0 for transient, compound and final, 1 for
interactive, 3 for delegation, 5 for parallel — and it measures **what the scenario has to supply
that the runtime cannot**, not how many lines the scaffold will contain.

The resolver is developer tooling: it runs from `machine:scenario` and `machine:scenario-validate`
and nowhere else. Nothing here changes what a running machine does.

## Before you upgrade

Three checks, and the first two are **ordered** — scale the caps before you capture anything, or the
capture is taken under a ceiling the upgrade will change.

1. **Scale any pinned `--max-iterations`.** The cap is now one budget for the whole resolution
   instead of one per branch of the trigger event. A multi-branch trigger therefore has less
   headroom than before: multiply a pinned value by the trigger's branch count. For
   `machine:scenario-validate`, whose single cap spans every trigger it checks, use the largest
   branch count in play.
2. **Capture the `machine:scenario` listing for any pinned `--path=N`.** The index re-orders. Save
   the listing and re-match by signature afterwards; there is no automatic migration in either
   direction.
3. **Check for a `ScenarioPath` subclass.** `$totalWeight` is a new readonly `int`. A subclass that
   already declares a property of that name is a **fatal** at upgrade time only if it declares a
   different type: property types are invariant, so `public float $totalWeight` becomes
   `Type of Sub::$totalWeight must be int`, while `public int $totalWeight` compiles and constructs
   normally. A subclass that overrides `__construct` without calling `parent::__construct` reaches a
   broken state by a different route, and is worse: no load-time signal, just a throw on the first
   read.

## Changed

- **`resolveAll()` returns paths sorted by weight, then by step count.** Previously the results were
  whatever order the search produced, appended one trigger branch after another and never sorted.
  Any test asserting that order, or indexing into it, is affected. *Remedy: none needed — re-read
  the order from the new listing.*

- **`--path=N` re-indexes.** A saved invocation that selected path 3 now selects a different route,
  usually with no error. Under a cap the listing can also shrink, in which case the index fails out
  of range instead. *Remedy: capture the listing before upgrading and re-match by signature.*

- **`--max-iterations` is one budget for the whole resolution.** It was one per trigger branch, so
  the effective ceiling was `maxIterations × branchCount`. Operators who never pinned the flag lose
  the same headroom silently, since the default stays 1000. *Remedy: multiply a pinned value by the
  branch count.*

- **Truncation becomes more likely, never less.** The smaller effective ceiling above is the whole
  of the reason: `wasTruncated()` can report `true` where it reported `false` on an unchanged machine
  at an unchanged cap. Cost ordering has a separate consequence rather than a shared one — it defers
  a target reachable only through an expensive state behind every cheaper frontier entry, so a target
  a cap previously reached may now fall outside it, but it cannot move the flag, since draining the
  frontier costs the same number of expansions in any order. *Remedy: raise `--max-iterations`.
  "Truncated at the search limit" remains a different finding from "no path exists", and only the
  first is fixable this way.*

- **`machine:scenario`'s operator-facing text changes three times.** Each listed path's stats line
  gains a trailing `weight N`; both commands' `--max-iterations` description no longer calls the
  search BFS or the cap per-branch; and a **single-path resolution now prints a listing where it
  previously printed nothing at all**. The listing was gated on there being more than one path, so a
  one-route resolution emitted no header, no signature and no weight; it now emits all three, minus
  the `Use --path=N` hint, which is still shown only when there is something to select. That is the
  one of the three that changes output a script may currently be matching on emptiness. *Remedy:
  update any test asserting these strings, and any parser that treated "no listing" as "one path".*

- **`ScenarioPath` gains a serialised property.** `$totalWeight` appears in anything that serialises
  a path, so a snapshot over one changes. It is *derived* rather than accepted, so any hydration
  that bypasses the constructor — `unserialize()`, reflection-based rebuilding — leaves it
  uninitialised and reading it throws. On rollback the mirror applies: a path serialised by the new
  code and read back by the old class carries `totalWeight` as an undeclared property. `ScenarioPath`
  is a `readonly class`, which forbids dynamic properties outright, so `unserialize()` raises
  `Error: Cannot create dynamic property` unconditionally — on every supported PHP, whatever the error
  handler. It fails loudly rather than silently, but it does fail. *Remedy: do not
  carry a serialised `ScenarioPath` across the version boundary; regenerate it.*

- **The default scaffold changes.** A caller passing no flags gets the cheapest route, and that is
  often not the route it got before, so `machine:scenario` writes a different file for an unchanged
  machine. Committed scaffolds are neither regenerated nor migrated, and a regenerate-and-diff CI
  check will report drift on the upgrade commit. *Remedy: regenerate deliberately, and diff before
  merging — generated scaffolds are meant to be hand-edited, so a blind regenerate overwrites author
  work.*

## Added

- `StateClassification::weight(): int` — the single home for the scale, an exhaustive `match` with
  no default arm, so a seventh classification added without a weight fails loudly instead of pricing
  itself at 0.
- `ScenarioPath::$totalWeight` — a public readonly `int`, derived from the path's own steps.

## Rolling back

The upgrade actions do not simply reverse.

- **Divide the pinned caps back**, or the next upgrade compounds the multiplication.
- **Re-capture the listing** before downgrading: `--path=N` re-indexes in that direction too.
- **Decide what to do with regenerated scaffolds.** This is the one change that does not reverse on
  its own: a scaffold regenerated and committed while 9.20.0 was live outlives the downgrade, and
  the old resolver then disagrees with it. Either revert those commits with the release, or
  regenerate again afterwards.

## Notes

The change ships with two known risks, both recorded in the spec rather than fixed here.

An `@always` inherited from an ancestor classifies every descendant TRANSIENT, so a whole subtree is
priced at 0 — including a leaf a scenario can only enter by sending an event. Nothing in a state's
own definition reveals it. It is the scale's broadest under-price.

And the 0/1/3/5 scale itself has never been checked against a real machine. Only the *ordering* of
the six values is claimed; the exchange rates between them are not, and nothing validates them. A
later correction is a minor release under the same rule that governs this one.

Where the resolver's view of a definition differs from what the runtime does — four such places —
see `spec/draft-scenario-resolver-runtime-divergences.md`. All four predate this change and none is
fixed by it, but cost ordering makes several of those shapes more likely to win, so a route the
runtime refuses is easier to surface than it was.

The existing test suite passed unchanged through the whole change: 2995 tests, phpstan clean, 100%
type coverage.
