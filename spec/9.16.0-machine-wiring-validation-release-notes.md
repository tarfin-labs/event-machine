# Release Notes — 9.16.0 Machine Wiring Validation

`machine:validate` returns a real exit code and gains three wiring checks. **Read the upgrade
section before updating**: the command could not fail before this release, so turning it on
can surface problems that were always there.

## Before you upgrade

Upgrade on a branch or staging and run `php artisan machine:validate --all` **there**.
Running it on the current version proves nothing — that version always exits 0, which is the
false green this release removes.

## Added

- **Exit codes.** `0` when at least one machine validated and none produced findings; `1` on
  findings, an unresolvable machine, a missing definition, or a throw; `2` when called with
  neither a machine argument nor `--all`. `--all` discovering zero machines is a failure —
  a sweep that validated nothing must not read as clean.

- **Behavior-to-context compatibility.** A behavior whose `__invoke()` type-hints a context
  the machine does not declare raises a `TypeError` the first time its transition fires. The
  check reports it statically instead.

- **`$requiredContext` key checking.** A key the declared context class cannot supply is
  reported. The check errs toward silence: anything that might be satisfiable at runtime is
  left alone, because a false failure in a CI gate is worse than a missed one.

- **Event-type collision detection.** Two event classes deriving the same type collapse to
  one entry in the machine's event registry — and that registry is what reconstructs
  persisted events, so payload validation can come from the wrong class. The finding names
  the class that currently owns the type.

- **Class-first resolution for named machines.** Discovery recognises only classes that
  directly extend `Machine`, so a machine behind an intermediate base class was invisible to
  it. Naming such a machine now validates it instead of reporting it missing.

## Changed

- Both command paths run identical checks. `--all` and a named invocation previously reported
  the same machine differently — `warn()` versus `error()` for a missing definition, and two
  different exception messages.

- One named machine failing no longer stops the remaining named machines from being validated.

## Breaking

- **`handle()` changes from `void` to `int`**, as do the per-machine methods it delegates to
  (`validateMachine()`, `validateAllMachines()`). A consumer subclassing this command hits a
  **load-time fatal on a discovered console class**, which takes out every `php artisan`
  invocation — including the ones a deploy runs before migrations. Check for subclasses first.

- **The command can now fail.** Three consequences:
  - a CI pipeline already running `machine:validate --all` starts failing on machines that
    were silently invalid;
  - a test suite that copied the `assertSuccessful()` recipe from the docs has an assertion
    that has never been able to fail;
  - a scheduled run with `emailOutputOnFailure` has a dead alert hook that becomes live, so
    a project can start receiving recurring mail with no code change of its own.

- No opt-out flag is provided. The command is opt-in — a project that does not run it is
  unaffected — and a `--strict` escape would leave the default reporting a false green.

## Clearing a collision finding changes an event type

The remedy for two classes deriving the same type is to rename one or override its
`getType()`, and the derived type is what is written to `machine_events.type` and what
transitions are keyed by. For a machine with in-flight instances that is a wire-format change:

- Rows written before the change keep the old type string; a restored machine must still
  route them.
- The same applies to rows already in `machine_event_archives`, which a fix written against
  the events table alone would skip, and to queued job payloads carrying the retired string.
- **Overriding `getType()` on the class that does not currently own the type is usually the
  safer move** — it preserves both strings and touches no data. The finding names the current
  owner so you can tell which class that is.
- Rolling the release back does not undo a type change already written to rows.

## What a passing run does not guarantee

Two limitations feed the same exit code and neither makes the run fail: `--all` sees only
classes that directly extend `Machine`, and the `$requiredContext` check deliberately
under-reports. A green exit means no finding was produced, not that the wiring is complete.
