# Release Notes — 9.18.1 Scenario Deactivation on the Common Path

9.18.0's scenario deactivation landed in only one of `ScenarioPlayer`'s two exits, and not the one
ordinary scenarios take. This completes it.

## Fixed

- **A scenario with no continuation stayed armed after it finished.** `ScenarioPlayer` has two
  exits. 9.18.0 added the "deactivate when the scenario is done" rule to `executeContinuation()`
  but left `execute()` re-persisting unconditionally — and `execute()` is the path an ordinary
  scenario takes: activated once, no `continuation()`, running to a non-final target.

  So the common case still left `scenario_class` set forever, which is the precise case the 9.18.0
  fix was written for. `scenario_class` still did not mean "a scenario is in flight", and the
  readers that take it to mean that — including the resume path's own continuation check — still
  saw a scenario that was not in flight.

  Both exits now apply the same rule: deactivate on a final state or when the scenario has no
  continuation, re-persist otherwise.

## Severity

Cosmetic, not data-bricking. 9.18.0's guarantee that a stored scenario cannot make a machine
unloadable is intact and independently verified — the leftover rows cost nothing at load time. What
was left was a column that lied.

Rows left behind by 9.18.0 or earlier are not retroactively cleared. They are harmless; if you want
them clean, a one-off `UPDATE machine_current_states SET scenario_class = NULL, scenario_params =
NULL` over the finished ones is safe.

## Note on the response payload

Deactivating on this path cannot cost the endpoint response its `activeScenario` block: the
controller emits that block only when `hasContinuation()` is true, which is exactly the case where
the row is now left in place. The two conditions are complementary.
