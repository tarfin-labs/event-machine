# Release Notes — 9.18.0 Scenarios Cannot Brick a Machine

A finished scenario no longer stays armed, and stored scenario params are no longer re-validated
every time a machine loads — which could make a machine permanently unopenable. Also:
`machine:scenario-validate` names the scenario files it could not load and fails on them, and the
toolchain problems that left 9.17.0's CI red are repaired.

## Before you upgrade

**Two things can newly fail, both on problems that already existed:**

- A CI job running `machine:scenario-validate` starts failing on scenarios that were already broken
  and already not being exercised.
- If you have machines stuck at 500 with `ScenarioConfigurationException`, this release un-sticks
  them; you no longer need the manual `UPDATE` on `machine_current_states`.

## Fixed

- **A scenario could make a machine permanently unloadable.** `Machine::restoreStateFromRootEventId()`
  re-hydrated the stored scenario on every load, and `hydrateParams()` re-ran the full validator.
  Any rule that reads the world — `exists` on a row someone later deleted, `after_or_equal:today`
  once midnight passes — went from passing to failing with nothing about the machine having changed.
  The machine then threw on every load.

  It was unrecoverable through the application: the code that clears the stored scenario
  (`MachineController::maybeRegisterScenarioOverrides()`) runs *after* the restore, so it could
  never be reached. The only way out was a direct `UPDATE` on `machine_current_states`.

  Three changes, in the order they matter:

  1. **Stored params are hydrated without being re-validated.** Validation belongs to the moment
     params are accepted, and still happens there. `hydrateParams()` takes a `validate` flag; the
     three restore paths pass `false`.
  2. **A finished scenario is deactivated.** `ScenarioPlayer` deactivated only on a FINAL state, so
     a scenario that reached a non-final target with no continuation re-persisted itself and stayed
     armed forever. `scenario_class` now means "a scenario is in flight", which is what every reader
     of that column takes it to mean.
  3. **Nothing about a scenario can stop a machine loading.** The restore block drops the overrides
     rather than the machine if anything at all goes wrong hydrating a stored scenario. A QA aid
     must never make a machine unopenable, whatever is wrong with it.

  Found by a consumer on 9.17.0: 24 rows across 12 machines were still holding `scenario_class`
  after their scenarios had finished, and one bricked application was enough to knock a user's
  session to the login page.

- **A scenario that could not be loaded vanished instead of failing.** Discovery skips a file when
  nothing loads under the class name its path implies, or when the class loads but cannot be
  constructed. Skipping is right — one broken file must not stop the others being validated — but
  it was done silently, so the command reported a smaller total and exited `0`. A scenario broken
  in its class body was indistinguishable from one nobody had written.

  The comment in the source made it worse by claiming the validate command caught these later. It
  cannot: that command takes its list from the same method that dropped them.

  This was found by a consumer upgrading to 9.17.0, whose `machine:scenario-validate` surfaced a
  scenario dead since an unrelated namespace move. That one was reachable because its `plan()` was
  the broken part; had the breakage been in the class body it would have vanished from the count.

- **`Machine::resolveOutputBehavior()` handed an unresolvable output definition to `resolve()`.**
  A definition that is neither a string nor a callable produced a container error naming neither
  the machine nor the state it came from. It now throws `MachineOutputResolutionException` naming
  the type it received.

- **The `symfony/process` dev constraint excluded what actually installs.** It was `^6.0|^7.0`
  while this package supports Laravel 11/12/13, i.e. symfony 7 and 8. With a gitignored
  `composer.lock` that meant contributors resolved a different dependency tree than CI did, which
  is how 9.17.0 shipped with a red static-analysis gate. Now `^7.0|^8.0`.

## Added

- **`ScenarioDiscovery::skippedFor(string $machineClass)`** returns the files discovery found but
  never validated, as `list<array{file: string, class: string, reason: string}>`.

- **`machine:scenario-validate` reports them**, with a count that makes the gap visible:

  ```
    12 scenario files found, 11 validated — 1 could not be loaded:
    ✗ AtAllocationUnderReviewScenario  (not validated)
      class not found — the file does not declare App\Machines\CarSales\Scenarios\AtAllocationUnderReviewScenario

  Total: 11 passed, 1 not loaded
  ```

## Breaking

- **`machine:scenario-validate` exits `1` when a scenario file could not be loaded.** Previously
  such a file left the list and the command exited `0` with a smaller total. Both call paths — a
  named machine and the discovery sweep — now count it.

  A `--scenario` filter is unaffected: narrowing the list is the point, so the excluded files are
  not reported as skipped.

## Note on 9.17.0

9.17.0 is a valid release and its runtime behaviour was verified against three production machines,
but its CI run was red: the Rector job failed on the dependency drift described above, and because
Rector gates the pipeline, the test, static-analysis and mutation jobs were skipped. 9.18.0 is the
first release in this line with a green pipeline. Nothing in 9.17.0's runtime behaviour changed as
a result of the fixes — what failed were static gates and a dev-only constraint.
