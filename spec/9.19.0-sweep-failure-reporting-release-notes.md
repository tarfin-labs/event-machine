# Release Notes — 9.19.0 Sweep Failures Are Failures

`machine:process-scheduled` and `machine:process-timers` used to exit `0` when they had done
nothing because something broke. They now fail. A scheduled machine in several parallel regions is
also no longer dispatched once per region.

## Before you upgrade

**A scheduled command can newly fail** — on problems that were already there and already silent.
If a cron monitor watches these commands, it will start reporting what it was previously blind to.
Run both once by hand before trusting the schedule.

## Fixed

- **A throwing schedule resolver exited SUCCESS.** `ProcessScheduledCommand` caught the throwable,
  printed it, and returned an empty instance list — which `handle()` then reported as
  "No matching instances found" and exited `0`. "The resolver blew up" and "nothing to process"
  were indistinguishable, so a cron monitor stayed green while nothing was dispatched. The failure
  is now a `ScheduleResolverFailedException` that fails the command.

- **A machine whose `definition()` throws made the timer sweep exit SUCCESS.**
  `ProcessTimersCommand::processClass()` returned `void`, so `handle()` returned `SUCCESS`
  regardless. A machine whose definition stopped building swept nothing while the schedule running
  it looked healthy.

- **A parallel machine was dispatched once per active region.** `machine_current_states` holds one
  row per region, and both the resolver cross-check and the root-level auto-detect plucked
  `root_event_id` without `distinct()`. One instance in N regions produced N identical
  `SendToMachineJob`s. Timers were never affected — they filter by a single `state_id`, and the
  primary key allows only one row per (instance, state) — and there is now a test that says so.

## Changed

- **`ProcessTimersCommand::processClass()` returns `bool` instead of `void`.** It is `protected`,
  so a consumer subclassing this command to override it must update the signature. A machine with
  no timers returns `true`: sharding runs this per class, and having nothing to do is not a failure.

- **The agent skill is current with 9.18.x.** Two entries were stale in ways that would mislead:
  `machine:scenario-validate` was described without its non-zero exit on unloadable scenario files,
  and a diagnostic step told readers to treat a null `scenario_class` as a dispatch failure — which
  since 9.18.1 is the normal state of a finished scenario. Two gotchas were added: `params()` rules
  are checked once at activation, and a scenario file that cannot load is a failure, not an absence.

## Internal

- `PathEnumerator::handleParallel()` carried the `@done` and `@fail` walks as two near-identical
  36-line blocks. They are now one `followParallelOutcome()`. Measured across all 5,957 functions
  in the repo: the method went from cognitive complexity **80 / 351 lines to 55 / 286**, and the
  extracted method is 10 / 51. This was a written commitment in the previous release's spec (§12
  D4), due since 9.18.0.

## A note on how the sweep bugs were found

All four shipped as characterisation tests parked outside `tests/` — they described the bugs
faithfully and were red on purpose, so the suite stayed green while the behaviour stayed wrong.
They are now in `tests/Features/SchedulesTimerSweepFailureTest.php` and green for the right reason.
Three of the four are the same shape this release line has been working through since 9.16.0:
a command that catches a failure and then reports success.
